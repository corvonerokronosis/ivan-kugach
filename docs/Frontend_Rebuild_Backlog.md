# Технический бэклог переработки frontend

## Сайт о творчестве Ивана Кугача

Версия документа: 1.0  
Дата формирования: 2026-06-19  
Назначение: рабочий бэклог перехода от single-file прототипа к структурированному многостраничному frontend-проекту  
Текущий источник поведения: `index_masterskaya.html`  
Целевой стек: Astro + TypeScript + CSS + изолированные клиентские модули интерактивов

---

## 1. Цель переработки

Перевести текущий proof-of-concept из одного HTML-файла в полноценный frontend-проект, который:

- имеет настоящие страницы и стабильные URL;
- собирается предсказуемой production-командой;
- разделяет разметку, стили, данные и интерактивную логику;
- сохраняет существующий визуальный образ мастерской и работающие сценарии;
- позволяет развивать каталог и контент без редактирования большого HTML-файла;
- подготовлен к последующему подключению CMS и backend, но пока от них не зависит;
- имеет автоматические проверки и понятный процесс ручного QA.

Ключевой принцип миграции: не переписывать весь прототип одним большим изменением. Каркас, страницы и интерактивы переносятся последовательно, а текущий `index_masterskaya.html` сохраняется как рабочий визуальный и функциональный эталон до завершения миграции.

## 2. Что входит в этот бэклог

- создание Astro-проекта;
- TypeScript и структура исходников;
- production-сборка и локальный preview;
- маршруты и настоящие страницы;
- общие layout и компоненты;
- перенос визуальной системы мастерской;
- перенос narrative-маршрута;
- перенос трёх интерактивов;
- модель данных каталога, серий и сюжетных материалов;
- frontend-форма заявки без реальной отправки;
- адаптивность и доступность;
- оптимизация загрузки изображений;
- SEO-основа на уровне frontend;
- автоматические проверки;
- техническая документация проекта.

## 3. Что пока не входит

- выбор домена и хостинга;
- production-деплой;
- Strapi или другая CMS;
- база данных;
- настоящая отправка заявок;
- email, Telegram, CRM и другие интеграции;
- авторизация сотрудников;
- онлайн-оплата;
- автоматическое резервирование;
- юридическое утверждение текстов;
- аналитика и cookie-consent;
- многоязычность.

При этом frontend должен быть устроен так, чтобы данные будущей CMS можно было подключить вместо локальных данных без повторной переделки страниц и компонентов.

## 4. Текущее техническое состояние

Актуальный прототип находится в `index_masterskaya.html`.

На момент аудита:

- один HTML-файл содержит более 5 200 строк;
- CSS занимает более 2 400 строк внутри `<style>`;
- JavaScript занимает более 2 100 строк внутри `<script>`;
- все экраны находятся в одном DOM и переключаются через класс `hidden`;
- адрес страницы не меняется при переходе между разделами;
- каталог работ, narrative-последовательности и hotspots хранятся в JS-константах;
- в коде зарегистрировано около 70 обработчиков событий;
- формы валидируются только в браузере и имитируют успешную подготовку заявки;
- изображения в `src/` занимают около 25,6 МБ;
- сборщик, package manager scripts, TypeScript и автоматические тесты отсутствуют;
- синтаксис текущего встроенного JavaScript корректен;
- все используемые локальные изображения существуют;
- дублирующихся HTML `id` не обнаружено.

Текущее состояние приемлемо как proof-of-concept, но создаёт риски при развитии: глобальное состояние, сильная связанность экранов, отсутствие маршрутов, тяжёлые изображения и невозможность независимо проверять части приложения.

## 6. Логика технических версий

### Frontend v0.1. Каркас и безопасная миграция

Цель: создать запускаемый Astro-проект рядом с текущим прототипом, не ломая эталон.

Результат:

- проект запускается через `npm.cmd run dev`;
- production-сборка создаётся через `npm.cmd run build`;
- preview запускается через `npm.cmd run preview`;
- есть базовый layout, глобальные стили и пустые маршруты;
- текущий прототип продолжает открываться отдельно.

### Frontend v0.2. Многостраничная оболочка

Цель: перенести обычные контентные разделы и навигацию на настоящие маршруты.

Результат:

- есть главная, страница художника, каталог, архив и страницы работ;
- навигация работает обычными ссылками;
- обновление страницы и прямой вход по URL не ломают интерфейс;
- данные каталога не находятся внутри компонентов.

### Frontend v0.3. Интерактивный маршрут

Цель: перенести narrative-систему и три интерактива без потери поведения.

Результат:

- каждый интерактив изолирован в собственном модуле;
- интерактивы не загружают код друг друга;
- маршрут между ними работает через URL и явные переходы;
- прогресс активного интерактива хранится только локально в его модуле.

### Frontend v0.4. Качество интерфейса

Цель: довести адаптивность, доступность и загрузку ресурсов до уровня полноценного сайта.

Результат:

- оптимизированы изображения;
- пройдены целевые desktop, tablet и mobile viewport;
- модальные окна и управление доступны с клавиатуры;
- отсутствует горизонтальное переполнение;
- основные страницы имеют корректные метаданные.

### Frontend v1.0. Готовый frontend

Цель: получить поддерживаемую production-сборку, готовую к отдельному этапу интеграции с CMS и backend.

Результат:

- все актуальные сценарии перенесены;
- single-file прототип больше не является точкой входа;
- локальная модель данных соответствует будущему CMS-контракту;
- проверки выполняются одной командой;
- есть документация по структуре, контенту и ручному QA.

## 7. Правила ведения бэклога

Статусы:

- `[ ]` — не начато;
- `[~]` — в работе;
- `[x]` — завершено;
- `[!]` — заблокировано.

Приоритеты:

- **Must** — обязательно для Frontend v1.0;
- **Should** — желательно выполнить до Frontend v1.0;
- **Could** — можно отложить без разрушения архитектуры.

Задача считается завершённой только после выполнения её критериев готовности и указанной проверки. Простого наличия кода недостаточно.

## 10. Критерии готовности Frontend v1.0

Frontend-переработка считается завершённой, если:

- основной проект запускается и собирается через npm-команды;
- `index_masterskaya.html` больше не является основной реализацией;
- главная, художник, каталог, архив, серии, работы и интерактивы имеют отдельные URL;
- обновление любой страницы не ломает её состояние;
- каталог, narrative и hotspots находятся в типизированных данных;
- страницы и карточки не дублируют модель произведения;
- три интерактива изолированы и не используют общее глобальное состояние;
- код интерактивов загружается только на соответствующих страницах;
- форма честно работает как frontend-заглушка и готова к подключению API;
- изображения проходят оптимизирующий pipeline;
- основные маршруты работают на целевых viewport;
- все dialogs и основные действия доступны с клавиатуры;
- отсутствуют критические runtime, TypeScript, lint и accessibility ошибки;
- `npm.cmd run verify` выполняется успешно;
- README, инструкция по контенту и QA-checklist отражают текущую реализацию.
