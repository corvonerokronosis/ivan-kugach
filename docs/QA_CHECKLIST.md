# Manual QA checklist

Ручной checklist для Astro-кандидата перед `FRT-062`. Он дополняет
автоматическую проверку `npm.cmd run verify`, но не заменяет её.

## Подготовка

1. Выполнить `npm.cmd run verify`.
   Ожидаемый результат: команда завершается с кодом `0`, этап smoke выводит
   `Browser smoke result: PASS`, в `dist/` лежит свежая production-сборка.
2. Выполнить `npm.cmd run preview`.
   Ожидаемый результат: Astro preview запускает локальный URL без ошибок
   PowerShell; все дальнейшие проверки выполняются в production preview, а не в
   dev server и не в `index_masterskaya.html`.
3. Открыть DevTools Console.
   Ожидаемый результат: при прямом входе, навигации, обновлении страницы,
   интерактивах и отправке frontend-формы нет `error`, failed local requests или
   404 для ассетов.

## Маршруты

1. Открыть `/`, обновить страницу.
   Ожидаемый результат: виден первый экран мастерской с одним `h1`, navigation,
   CTA интерактивного маршрута и ссылками на каталог; после refresh состояние не
   ломается.
2. Открыть `/artist/`, `/experience/`, `/works/`, `/archive/`.
   Ожидаемый результат: каждый URL отдаёт самостоятельную страницу с header,
   footer, корректным заголовком и без перехода в legacy-монолит.
3. Открыть `/works/dor-3518/` и `/series/demo-series-needs-title/`.
   Ожидаемый результат: generated-страницы открываются напрямую и после refresh,
   показывают ожидаемые данные работы или серии, а ссылки внутри страницы ведут
   на существующие Astro URL.
4. Открыть неизвестный URL, например `/works/not-a-real-work/`.
   Ожидаемый результат: пользователь попадает на оформленную 404-страницу с
   понятной навигацией обратно к основным разделам.

## Каталог, карточка работы и форма

1. На `/works/` проверить карточки каталога.
   Ожидаемый результат: доступны три карточки основного каталога, две архивные
   работы отделены по статусу, цены и статусы не отличаются от локальных данных.
2. Открыть карточку `Дорога`.
   Ожидаемый результат: URL меняется на `/works/dor-3518/`, видны изображение,
   параметры, описание, связанная серия или подборки и CTA заявки.
3. Нажать `Подготовить заявку` без заполнения обязательных полей.
   Ожидаемый результат: форма показывает валидацию рядом с полями и не сообщает
   об отправке.
4. Заполнить имя, email и согласие, затем снова нажать `Подготовить заявку`.
   Ожидаемый результат: появляется frontend-only подтверждение подготовки
   заявки; текст не обещает бронь, оплату, email, CRM или backend-отправку.

## Narrative

1. Открыть `/experience/` и перейти к началу маршрута.
   Ожидаемый результат: CTA ведёт на `/experience/story/intro/`.
2. Последовательно пройти `/experience/story/intro/`,
   `/experience/story/bridge/`, `/experience/story/light-bridge/` и
   `/experience/story/finale/`.
   Ожидаемый результат: на каждой странице видны номер/прогресс, изображение,
   текстовый блок и CTA следующего шага; direct entry и refresh сохраняют
   корректное состояние.
3. Проверить финальный CTA.
   Ожидаемый результат: финал ведёт к каталогу или следующему ожидаемому
   продуктовым маршрутом действию без обращения к legacy `showScreen`.

## Интерактивы

1. Открыть `/experience/color-return/`.
   Ожидаемый результат: canvas-stage загружает картину, progress отображается,
   pointer-жест или кнопка completion открывает dialog завершения; повторный
   запуск сбрасывает progress к `0%`.
2. Открыть `/experience/details/`.
   Ожидаемый результат: кнопки zoom, wheel, drag, reset и hotspots работают;
   hotspot открывает dialog, просмотр всех точек открывает completion dialog.
3. Открыть `/experience/light/`.
   Ожидаемый результат: выбор работы, range состояний света, progress dots,
   reset и completion dialog работают; переход `Открыть финальную вставку` ведёт
   на ожидаемый narrative URL.

## Dialogs и keyboard navigation

1. Пройти основные страницы клавишей `Tab`.
   Ожидаемый результат: skip-link, brand, navigation, CTA, карточки, controls и
   поля формы получают видимый focus в логичном порядке.
2. Открыть любой native dialog интерактива.
   Ожидаемый результат: focus переносится внутрь dialog, `Escape` закрывает его
   там, где закрытие разрешено, а focus возвращается на инициирующий элемент.
3. Проверить keyboard-only сценарии формы, zoom/details controls и light range.
   Ожидаемый результат: все ключевые действия доступны без мыши и не создают
   скрытого горизонтального scroll.

## Viewport Sweep

Использовать матрицу из `docs/QA_VIEWPORTS.md`:

| Профиль         | Viewport   | Ожидаемый результат                                                                                             |
| --------------- | ---------- | --------------------------------------------------------------------------------------------------------------- |
| Desktop         | `1440x900` | Все основные страницы помещаются без горизонтального overflow; baseline-размер подходит для сравнения с legacy. |
| Compact desktop | `1180x760` | Header, карточки, stage и controls не перекрываются при меньшей высоте.                                         |
| Tablet portrait | `820x1180` | Контентные страницы и интерактивы перестраиваются без обрезания CTA и dialog.                                   |
| Mobile          | `390x844`  | Основные mobile-состояния совпадают с baseline-ожиданием и проходят completion/dialog-сценарии.                 |
| Narrow mobile   | `360x800`  | Самый узкий layout не имеет горизонтальной прокрутки, а 404 и generated-страницы остаются читаемыми.            |

Для каждого размера:

1. Открыть страницы, перечисленные для профиля в `docs/QA_VIEWPORTS.md`.
   Ожидаемый результат: direct entry и refresh работают на каждом URL.
2. Проверить первый viewport и full-page scroll.
   Ожидаемый результат: нет горизонтального overflow, clipping текста,
   перекрытия controls, dialog или footer.
3. Для визуальных изменений свериться с `docs/VISUAL_BASELINE.md`.
   Ожидаемый результат: отличия либо намеренные и описаны в
   `docs/QA_VIEWPORTS.md`, либо оформлены как follow-up до переключения.

## Финальная отметка

1. Убедиться, что `npm.cmd run verify` и ручной проход завершены после последних
   изменений.
   Ожидаемый результат: автоматические проверки зелёные, а ручные замечания либо
   исправлены, либо явно вынесены в отдельные задачи.
2. Перед `FRT-062` открыть `docs/ENTRYPOINT_CUTOVER_PLAN.md`.
   Ожидаемый результат: все gates, включая этот QA-checklist, закрыты до
   архивации legacy-точки входа.
