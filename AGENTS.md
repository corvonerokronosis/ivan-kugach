# AGENTS.md

Короткая инструкция для будущих сессий Codex. Цель — быстро найти нужные файлы, не тратить токены на полный обход репозитория и не перепутать текущую Astro-версию с архивным legacy-прототипом.

## С чего начинать

1. Открой `docs/PROJECT_MAP.md`.
2. Выполни `git status --short`.
3. Если нужен список файлов, используй `rg --files` или `git ls-files`.
4. Для текущего поведения смотри Astro-маршрут, компонент, данные или скрипт из `src/` по карте проекта.
5. Для выбора профильного документа используй `docs/README.md`.
6. Для исторической или визуальной сверки используй `docs/LEGACY_REFERENCE.md`.
7. Перед созданием Astro-файлов проверь правила в `src/README.md`.
8. `README.md` используй для краткого описания продукта и пользовательского маршрута.

Не читай весь `archive/index_masterskaya.html` целиком без необходимости. Для исторической сверки сначала найди нужный экран, функцию, константу или CSS-класс через `rg`.

## Источник текущей правды

- `src/pages/index.astro` и Astro route `/` — единственная поддерживаемая исходная главная страница.
- `src/` содержит актуальные Astro-страницы, компоненты, данные, стили, клиентские модули и production-изображения.
- `src/layouts/BaseLayout.astro` владеет общей оболочкой: статическим header, обязательным footer, подключением глобальной темы и progressive-enhancement мобильного меню. Route-файлы не дублируют эту ответственность.
- `archive/index_masterskaya.html` — исторический legacy-reference; не участвует в build и production.
- `src/README.md` фиксирует ответственность директорий и правила именования нового кода.
- `experiments/` — отдельные визуальные и механические эксперименты.
- `archive/` — старые версии и история.
- `docs/README.md` перечисляет только активную документацию текущего Astro-контура.
- `docs/LEGACY_REFERENCE.md` объединяет статус архивной точки входа, functional reference и visual baseline.

Если документация расходится с текущим кодом, доверяй Astro-коду в `src/` и явно отмечай расхождение.

## Как искать

- Сначала список файлов:

```powershell
rg --files
```

- Ищи точечно:

```powershell
rg -n "landingScreen|experienceScreen|salesScreen" archive/index_masterskaya.html
rg -n "SALES_WORKS|NARRATIVE_SEQUENCES|HOTSPOTS|LIGHT_WORKS" archive/index_masterskaya.html
rg -n "showScreen|goToExperience|fitExploreView|updateLightState" archive/index_masterskaya.html
```

- Для стилей ищи по классу конкретной зоны:

```powershell
rg -n "\.sales-|\.explore-|\.light-|\.narrative-|\.modal" archive/index_masterskaya.html
```

- `.git/`

- `build/`
- `coverage/`
- `.astro/`
- `.codex_tmp_deps/`
- `.tmp/`, `tmp/`, `temp/`
- `experiments/`

- `scrns/`
- большие изображения в `src/`
- историю удалённых планов, changelog и требований в Git

Не открывай бинарные изображения как текст. Для визуальной проверки используй браузер или просмотр изображения.

## Работа с документацией

- Используй `docs/README.md` как индекс активных документов.
- `docs/` намеренно является local-only директорией через `.gitignore`: актуализируй документы в общей рабочей папке, но не добавляй их в Git принудительно без отдельного решения пользователя об изменении этой политики.
- Не создавай отдельный changelog, одноразовый аудит или новый план, если
  актуальный результат можно зафиксировать в существующем рабочем документе.
- Завершённую историю оставляй Git; не возвращай удалённые до-Astro документы
  в активный набор без явной необходимости.
- Не используй архивный legacy-прототип как источник новых продуктовых
  изменений. Baseline PNG сохраняй только как исторический visual reference.

## Текущие команды

В проекте создан Astro production-контур. Доступные команды:

```powershell
npm.cmd install
npm.cmd run dev
npm.cmd run check
npm.cmd run lint
npm.cmd run test:unit
npm.cmd run format
npm.cmd run format:check
npm.cmd run build
npm.cmd run preview
npm.cmd run test:smoke
npm.cmd run test:smoke:dist
npm.cmd run performance:budget
npm.cmd run verify
```

`lint` проверяет новый Astro/TypeScript-код через ESLint. `format` исправляет форматирование нового production-контура и активной документации, а `format:check` только проверяет его. Обе команды явно используют `.prettierignore`, поэтому local-only `docs/` проверяется несмотря на правило в `.gitignore`.

`verify` последовательно запускает typecheck, lint, unit-тесты, format-check,
production build, performance budget и browser smoke по готовому `dist/`.

Архивный legacy HTML, `archive/`, `experiments/`, generated output и временные директории исключены из ESLint и Prettier.

Для архивного legacy-reference:

1. Открой `archive/index_masterskaya.html` в браузере.
2. Проверь исторический экран или связанный пользовательский маршрут только для сверки.

Для быстрой проверки встроенного JavaScript:

```powershell
node -e "const fs=require('fs');const s=fs.readFileSync('archive/index_masterskaya.html','utf8');const m=s.match(/<script>([\s\S]*?)<\/script>/i);new Function(m[1]);console.log('Archived inline JS syntax OK')"
```

Команда `test` уже доступна как alias для `test:unit`.

На Windows предпочитай `npm.cmd`, не меняя PowerShell execution policy.

Текстовые файлы репозитория фиксируются с LF через `.gitattributes`. Не меняй
это правило локальными массовыми преобразованиями в CRLF: иначе Codex и Git
могут показывать ложные изменения без содержательного diff.

## Правила изменений

- Перед изменениями обнови `origin/main` и создай от него отдельную ветку
  `codex/<short-task-name>`; не работай напрямую в `main`.
- Коммиты и push выполняй только из текущей `codex/*`-ветки. Не push и не merge
  в `main` без отдельной явной команды пользователя.
- Сохраняй русский язык видимого интерфейса, если пользователь явно не попросил иначе.
- Не изменяй продуктовые тексты, цены, статусы и факты о работах без явной задачи.
- Не подключай CMS, backend, настоящую отправку заявок или хостинг в рамках frontend-бэклога.
- Не добавляй React/Vue только ради отдельных интерактивов; текущий стек — Astro + TypeScript + DOM/Canvas modules.
- Не копируй весь встроенный CSS и JavaScript в один новый файл при миграции: разделяй по ответственности.
- Не доверяй архивному legacy HTML и старым экспериментам как источнику актуального поведения.
- Сохраняй пути к изображениям и учитывай регистр и пробелы в текущих именах.
- Не перезаписывай unrelated изменения пользователя в грязном worktree.

## Обязательный пайплайн независимых субагентов

Субагенты в этом проекте используются для независимой проверки, а не для
реализации. Пока пользователь явно не попросил иначе, основной агент сам вносит
изменения; не делегируй написание production-кода встроенному `worker` или другим
write-capable агентам.

Проектные проверщики находятся в `.codex/agents/`:

- `reviewer` — обязательный независимый финальный review любой задачи, которая
  изменяет файлы репозитория;
- `logic_auditor` — проверка TypeScript/JavaScript, данных, маршрутов, state,
  lifecycle, forms, browser history и интерактивных контрактов;
- `ui_qa` — реальная browser-проверка пользовательского UI, responsive,
  interactions, console, keyboard/focus, dialogs и themes.

### Когда кого вызывать

После завершения реализации и профильных автоматических проверок, но до
финального ответа пользователю:

1. **Всегда** запусти отдельного `reviewer`, если в рамках задачи изменён хотя бы
   один файл репозитория. Это обязательный gate и не заменяется self-review
   основного агента, `git diff`, `verify` или тем, что изменение кажется маленьким.
2. Дополнительно запусти `logic_auditor`, если diff затрагивает хотя бы одну из
   областей: `src/**/*.ts`, client-side script, data/repository/types, route
   contract, form validation/state, browser history, interactive engine/controller
   или связанный unit/smoke test.
3. Дополнительно запусти `ui_qa`, если результат изменения видим или достижим в
   браузере: Astro page/component/layout/style, navigation, content layout,
   form/dialog, responsive behavior, theme, motion или любой интерактив.
4. Если применимы несколько проверщиков, запускай их независимо и по возможности
   параллельно. Не передавай одному reviewer выводы другого до завершения их
   собственных проверок.
5. Передай каждому проверщику исходный запрос пользователя, критерии приёмки,
   baseline/base branch, изменённые файлы и diff или точные ссылки на него.
   Попроси проверить результат самостоятельно и вернуть findings с severity и
   evidence.
6. **Дождись завершения всех обязательных субагентов. Не формируй финальный ответ,
   пока хотя бы один required reviewer ещё работает.**

Если инструмент субагентов временно недоступен или обязательный reviewer не
стартует/падает, не подменяй его молча собственной проверкой. Повтори запуск в
разумных пределах; если runtime всё равно не даёт выполнить gate, явно считай
независимую проверку незавершённой и сообщи это пользователю.

### Review loop

- `BLOCKER` или `HIGH`: основной агент обязан проверить finding, исправить его в
  текущем scope, повторить затронутые автоматические проверки и заново вызвать
  того же профильного reviewer. Финализировать задачу с подтверждённым
  `BLOCKER/HIGH` нельзя.
- `MEDIUM`: исправь в текущей задаче, если это не расширяет согласованный scope;
  иначе явно вынеси в итог как follow-up с причиной.
- `LOW`: исправляй только если это локально и не создаёт лишний diff; иначе можно
  перечислить как необязательное наблюдение.
- Если finding оказался false positive, основной агент должен зафиксировать
  короткое техническое обоснование и не менять код ради удовлетворения reviewer.

После каждой итерации reviewer должен проверять актуальный diff, а не прежнюю
версию. Финальный отчёт пользователю включает, какие субагенты были запущены,
их итог `PASS`/findings и какие замечания были исправлены или осознанно оставлены.

### Browser QA и Playwright approvals

Этот раздел обязателен для основного агента и всех субагентов, включая `ui_qa`.
Для рутинного browser QA используй действия, явно разрешённые проектными
`.codex/rules/default.rules`. Команда, совпадающая с `decision = "allow"`, не
требует дополнительного пользовательского approval.

Для обычной проверки используй default in-memory Playwright CLI session без
`--session`/`-s`: это позволяет rules ограничивать разрешение конкретными
action-командами, а не широким session-scoped префиксом. Каноническая форма:

```powershell
npx.cmd --package @playwright/cli playwright-cli <action> [args...]
```

Допустима эквивалентная форма с `--yes` сразу после `npx.cmd`. Не переставляй
аргументы и не добавляй shell-wrapper, если прямой вызов доступен.

Без нового пользовательского approval выполняй только actions, перечисленные в
`.codex/rules/default.rules`. Текущий обычный QA-набор включает
snapshots/screenshots, поиск по snapshot, клики и формы, клавиатуру и мышь,
resize, dialogs, Back/Forward/reload, безопасную работу со вкладками,
console/request inspection, locator generation/highlight и close.

`open` и `goto` намеренно не входят в allowlist: prefix-rule не может
одновременно разрешить action и запретить произвольный последующий URL. Для них
действует обычная policy-проверка. Навигацию выполняй только по локальному
тестовому preview (`localhost`, `127.0.0.1`, `[::1]`) и маршрутам проверяемого
приложения. `snapshot` и `screenshot` разрешены для рутинного QA; используй
стандартный autogenerated output и не задавай произвольный `--filename`.

Не считай Playwright в целом заранее разрешённым. В обычный no-approval QA-контракт
не входят `eval`, `run-code`, `upload`, `drop`, state/cookies/localStorage/
sessionStorage mutation, route/network interception, `attach`, persistent/profile,
tracing/recording/video/PDF, `delete-data`, `close-all`, `kill-all` и другие
actions, отсутствующие в allowlist. Для них действует обычная policy-проверка и
при необходимости отдельный approval.

Не оборачивай разрешённую команду в `pwsh -Command`, `powershell -Command`,
`cmd /c`, произвольный скрипт или другой shell-wrapper: rules сопоставляют argv
буквально, и такая обёртка перестаёт совпадать с разрешённым Playwright-rule.
Если агент сначала выбрал несовпадающую форму, нормализуй её до прямого
`npx.cmd ... playwright-cli <action>` и повтори один раз без обращения к
пользователю. Не разрешай широкий `pwsh -Command` только ради Playwright.

Именованную Playwright session (`--session`/`-s`) создавай только когда реальная
изоляция браузерных контекстов нужна самой задаче. Такой вызов намеренно не
покрывается обычным no-approval allowlist и проходит стандартную policy-проверку.
Если rules были созданы или изменены уже после старта текущей Codex-сессии,
учитывай, что они загружаются при старте: сообщи о необходимости перезапуска
сессии вместо серии одинаковых approval-запросов.

## Минимальные проверки

Для правки архивного legacy-reference:

- проверить синтаксис встроенного JavaScript;
- проверить существование изменённых путей к ассетам;
- вручную пройти затронутый сценарий;
- проверить desktop и mobile, если менялась вёрстка;
- проверить консоль браузера.

Для Astro-кода:

- выполнить профильные проверки из задачи;
- выполнить `npm.cmd run verify`;
- открыть production preview;
- проверить прямой вход и обновление изменённых URL;
- убедиться, что страница не загружает код чужих интерактивов.

## Когда обновлять документацию

Обновляй `docs/PROJECT_MAP.md`, если:

- появилась новая реальная точка входа;
- добавились `package.json`, Astro pages, components, data или scripts;
- изменился основной маршрут;
- данные были вынесены из монолита;
- появилась новая команда проверки или сборки;
- директории переехали;
- legacy HTML перестал быть источником текущей правды.

Обновляй `AGENTS.md`, если изменился обязательный порядок работы, команды или источник текущей правды.

Не описывай планируемые файлы как уже существующие.

## Как отчитываться

В финальном ответе укажи:

- какие файлы изменены;
- какая задача бэклога выполнена, если применимо;
- какие проверки запускались и их результат;
- что не проверено вручную;
- короткий ручной сценарий проверки;
- обновлялись ли `PROJECT_MAP.md` или `AGENTS.md` и почему.
